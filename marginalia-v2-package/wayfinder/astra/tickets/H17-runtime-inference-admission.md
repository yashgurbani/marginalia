## Option A — Supported upstream admission
Keep the default runtime gated and own the requirement for a supported hook that freezes application content and resolved recipient, waits for host approval, then permits one physical attempt. Cover initial sampling, tool results, no-tool continuation, retries, fallback and compaction. Identify an owner and evidence for an upstream capability or contribution; do not assume a delivery date or that opening this ticket authorizes external outreach.

## Option B — Bounded HTTP-first fork prototype
Authorize a local experimental fork packet and synthetic fixture proof only, with a separately agreed time/effort cap. The prototype must:
- Trace final serialization and every physical HTTP attempt, including lower transport retries; freeze body bytes and actual recipient before any inference headers/body leave.
- Bind a one-use nonce to body digest, recipient, process epoch, request/attempt identity and expiry; changed bytes/recipient, replay, denial, cancellation or restart send zero bytes. Uncertain delivery consumes the nonce; retry requires fresh review.
- Exercise retry, deny, cancel, mutation, replay and unknown-outcome fixtures; cover repeated calls for tool results, compaction and `end_turn:false`. Record counted physical writes and exact approved/sent synthetic bytes.
- Keep WebSocket and unimplemented model paths unreachable in this **prototype**, with explicit refusal tests. Preserve all four product execution paths; prototype coverage is not feature completion.
- Use synthetic local transports by default: no auth contents, real-provider calls, account changes, private bearer extraction, or gateway deployment. Report limitations and stop at a reviewable patch/test packet before live validation or distribution.

## Tradeoffs and limits
Option A avoids taking on a modified runtime but has unknown availability. Option B can test the mechanism under local control and adds maintenance, transport-coverage and provider-support uncertainty. A gateway is not recommended because credential transit introduces a different trust arrangement; it is not selected by either option.

The child engineering estimate is 1–2 engineer-weeks for an HTTP prototype, 4–8 for fuller integration and adversarial fixtures, and 4–10 additional for three-OS packaging/live acceptance, with roughly ×2 uncertainty. These are unvalidated planning bands, not delivery promises or a budget approval. Yash may authorize a shorter first checkpoint and reassess.

Prototype success cannot close Q03/Q04/Q06, establish release readiness, prove confinement, or substitute for Windows/macOS/Linux acceptance. Supported subscription behavior, real replies, WebSocket coverage, platform packaging and production distribution remain separate evidence and decisions.
