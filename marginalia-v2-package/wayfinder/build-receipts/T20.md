### `finalizeDispatch` is not the solver's commit point, and must not become one

The obvious integration — reuse `ConsentSessionService.finalizeDispatch` as the gate —
is wrong, and this is the sharpest finding of the revision. That method consumes an
`allow-once` grant, inserts an `egress_events` row, and is keyed on a `JobSnapshot` with
a `provider`, a `policyKey` and a matching `consent_previews` row. A recompute has none
of those and **sends nothing anywhere**. Wiring it would spend the reader's this-time
cloud permission on local arithmetic and record an egress that never happened. Verified
present on `codex/t06-f20-atomic-handoff`, `origin/codex/pro-t06-full-recovery` and
`codex/t13-f20-consent`. The gate T06 owes is a separate, non-egress transaction.

### The defect: a committed claim for a handoff that never happened

`commit()` writes the durable claim and mints the lease; the service then makes its last
synchronous checks and can still refuse. **A workspace rebuilt between preparing the plan
and committing reaches that path**: the gate mints a lease on the current generation,
which is not the one this attempt hashed. Before this revision the service answered a
clean `generation-drift` rejection and walked away from a claim that was already durable.
Every later recompute of the same content then came back `already-claimed`, telling the
reader "a previous attempt was dispatched" when none ever was. The content became
permanently unrecomputable.

`SolverExecutionGate.releaseClaim?` is the fix: synchronous, for the same reason `commit`
is, and optional so no gate is assumed to have it. The service now withdraws the claim
where the gate can, and where it cannot it answers `outcome_unknown` naming that a claim
it cannot withdraw is standing — not a rejection implying the host is back where it
started. A release that throws is `outcome_unknown` too, carrying the host's own reason.
A `process-local` claim needs no withdrawal and still refuses cleanly.

### Interface compatibility, checked rather than assumed

## Corrections in revision 4 (chief review: execution boundary)

The one primary open item was the interrupted execution-boundary migration.

1. **One synchronous commit transaction.** The gate was `finalize(input):
   Promise<...>`. It is now `{ readonly durableAtMostOnce: boolean;
   prepareCommit(input): Promise<SolverPreparedCommit> }`, and
   `SolverPreparedCommit.commit()` is **synchronous**. Every await the decision
   depends on happens in `prepareCommit`; the single transaction (consume,
   authorize, egress, durable claim, handoff) happens in `commit()`. In
   `service.run` the checks after `commit()` are all synchronous, so `transport.exec`
   is the first await after the commit — no intervening await.
2. **A thenable commit is refused, not dispatched.** A `commit()` that returns a
   `Promise` reopens the boundary window, so the service answers `outcome_unknown`
   (`did not settle synchronously`) and runs nothing. A new test asserts the log
   stops at `prepareCommit`,`commit`.
3. **The standalone journal is removed; durable at-most-once lives in the gate.**
   `SolverAttemptJournal`/`SolverAttemptJournalEntry` are deleted. A `lookup` then a
   `record` across two calls is not atomic. `commit()` now returns
   `{ decision: 'already-claimed', state }` for a prior claim, and the committed
   decision carries `attemptClaim` (the strength it claimed under). The service
   reports the gate's `durableAtMostOnce` verbatim on `/api/solver/status`.

## Corrections in revision 3 (chief review)

1. **A real margin can construct a request.** The service computed a
   `policyFingerprint` from absolute host paths and demanded the browser's
   `policyKey` equal it, which no margin could produce; the tests synthesised it
   with private host arithmetic. `policyKey` is now gone from the wire. Instead
   `POST /api/solver/prepare` takes six client-visible fields and returns an opaque
   nine-field plan — `planId`, a single-use 64-hex `planToken`, `limits`,
   `expiresAt`, `modelTurns: 0` and the three identities. `POST /api/solver/recompute`
   runs one prepared plan on the reader's explicit click. Preparation starts no
   process, calls no gate, spends no grant and writes no file.
2. **Idempotency is bound to content, and results are re-authorized.** Settled and
   in-flight lookups key on `solverRequestIdentity`, not on `requestId`. A
   `requestId` reused for different content is refused as
   `request-identity-mismatch`. Every settled or polled read re-authorizes at a new
   `result-read` stage and re-checks the host-resolved principal. Stated plainly:
   a bounded evicting map cannot make at-most-once restart-safe, so
   `SolverAttemptJournal` is specified for T06 and every record honestly reports
   `atMostOnce: 'process-local'` until one is mounted.
3. **Always streaming, and both streams checked.** A raw-byte budget cannot bound a
   buffered JSON reply, because one control byte becomes a six-character escape.
   `SOLVER_ALWAYS_STREAMS` replaces `requiresStreaming`, so every call streams at
   any cap. `stderr` `capReached`, `hostBoundReached` and byte overrun now each
   reject as `output-invalid`; previously only `stdout` was checked.
4. **The abort listener is removed.** The transport's named `onAbortEvent` listener
   is detached in `finally`, and a synchronous `rpc.request` throw becomes a
   rejection inside the same `try` so the same cleanup runs. Terminate semantics
   are unchanged: the acknowledgement is still not proof the process exited.
5. **A committed generation lease is required.** Hashing a solver is a point
   observation, not an immutability guarantee, and path hardening does not close
   the window. `finalize` must now return a `SolverGenerationLease` minted in the
   same transaction as the handoff; a wrong generation, a wrong manifest or a lease
   that lapsed mid-run refuses the result as `generation-drift`. Refusing saved
   solvers outright was rejected as a non-fix.

### Two real defects the new tests found

- `plan-expired` was unreachable: `request()` swept expired plans before looking
  one up, so an expired plan was reported as `plan-unknown`. The lookup now runs
  first.
- The durable journal branch refused a hit under a new `requestId` as
  `request-identity-mismatch`. The journal is keyed by content identity, so that
  is exactly the case it exists to catch. The id comparison is deleted.

## What is NOT verified

- **No real Codex `command/exec` call was made.** Shapes now come from the installed
  generated schema rather than guesses, but no live app-server answered this code.
  **Real process evidence is still needed**: no observed exit code, no observed
  `capReached`, no observed terminate acknowledgement.
- **No real isolation was demonstrated on any platform**, win32 included. Test
  evidence is a consistent fixture that exercises `auditCodexPolicy`.
- **Real memory enforcement is unsupported.** Codex 0.153.4 `CommandExecParams` has
  no memory parameter. A request declaring `maxMemoryBytes` is refused with
  `limit-enforcement-unavailable` rather than quietly ignored. No T20 change can
  fix this; it needs an upstream capability.
- **Process stop on cancel is unconfirmed on every platform.** Late output is
  discarded, never delivered.
- **At-most-once is process-local.** No gate reporting `durableAtMostOnce: true` is
  mounted, so an eviction or a daemon restart would let the same identity dispatch
  again. No product surface may promise a reader a single run until such a gate lands.
- **No generation lease exists.** The refusals are tested against a double. Whether
  T06 will hold a workspace generation immutable for a lease's life is unverified,
  and that is what closes the artifact-drift window.
- **Authority and context are unmounted.** Every dependency interface has no
  implementation and there is no allow-by-default fallback, so the product state
  today is "no recompute runs", reported honestly.
